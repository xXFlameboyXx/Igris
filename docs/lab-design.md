# Secure Malware-Analysis Lab Design

Phase 0 does not implement dynamic analysis. This document defines the required
direction for future lab work.

## Environment Separation

Development environment:
Used for coding, unit tests, linting, and builds. It must use benign synthetic files
only and must not execute arbitrary suspicious binaries.

Application environment:
Runs the API, frontend, database, object storage, and workers. It may store hostile
files as data in future phases, but it must not execute them.

Isolated analysis environment:
Runs static parsers and reverse-engineering tools with least privilege and resource
limits. It should be treated as exposed to parser exploits.

Future sandbox environment:
Runs dynamic execution in disposable VMs or equivalent isolation. Each run should
start from a clean snapshot and be destroyed afterward.

## Sandbox Requirements for Future Phases

- No access to application secrets.
- No access to developer credentials.
- No direct access to production networks.
- Explicit network simulation or tightly controlled egress when needed.
- Snapshot restore or full disposal after every analysis.
- Per-analysis storage isolation.
- CPU, memory, disk, process, and wall-clock limits.
- Centralized audit trail that excludes raw hostile content.

## Development Test Data

Use benign synthetic files only. Examples include tiny text files, generated byte
patterns, and intentionally malformed but non-executable fixtures.

Do not commit live malware samples, weaponized documents, exploit kits, leaked
credentials, or real customer samples.
